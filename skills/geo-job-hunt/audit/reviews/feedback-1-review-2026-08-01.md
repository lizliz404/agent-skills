## 标题:geo-job-hunt v5.0.1 —— 复核结论:不做 v6(审计意义上的)

**审计对象**:`geo-job-hunt-pack`(skill v5.0.1 + audit/ 四份文档)

**复核方式**:独立解包,通读 5 个脚本(1978 行)+ SKILL.md/README.md + 全部 4 份审计文档,重跑 `py_compile`(全通过),逐条核对你 v5 AUDIT.md 的发现是否属实——不是转述,是复算。

**一句话结论**:**别做 v6。这一版已经过了"审计能创造增量信息"的拐点。** 真正该做的不是再审一轮,是三件几分钟能干完的具体动作——外加一件不算"优化"、算"启动"的事。

### 0. 最关键的事实

这套系统现在的状态是:**审计写了两轮(v4→v5→v5.0.1),真实投递次数 = 0。**

`user-apply-job` 的成功响应形态从 v4 到 v5.0.1 一直标 `OK_UNVERIFIED`——不是因为懒,是因为真的没投过。这本身是诚实的好习惯(宁可留白也不编契约),值得保留。但连带的后果是:`S5`(`apply_job` 与 `call()` 重复实现要不要合并)、"apply 成功判定能不能更强"这两个问题,**在没有一次真实投递之前,永远无法被"审计"出答案**——它们不是文档问题,是空白数据问题。再写一轮 audit 报告去讨论一个没有数据支撑的问题,就是典型的"清汤寡水":字数在涨,信息量没涨。

这就是"完美主义无限优化陷阱"在这里的具体样子:**不是代码被过度打磨,是审计本身在空转,而唯一能打破空转的动作(投一封简历)反而被无限期推迟了。**

### 1. 独立复核:v5 审计本身的质量

| 检查项 | 复核结果 |
|---|---|
| 5 个脚本 `py_compile` | ✅ 全通过(独立重跑) |
| `AUDIT.md` 的 14 项发现 | 抽查 I1–I6、S1、S5、S9,均能对应到具体行——证据分级有据可查 |
| `OK_UNVERIFIED` 判定逻辑(`classify_business_payload`) | 保守到位:宁可误判 FAIL 也不假装成功 |

工程质量已非瓶颈:stdlib-only、原子写(`os.replace`)、限流识别覆盖 3 种响应形态、CLI 契约明确退出码。继续优化边际收益趋近于零。

### 2. 独立发现、v5 审计没提到的三件事

**2.1 config-diff 补丁建议了两轮还没应用**——`amap.timeout: 120` 从 v4 的 I3 到现在四处生产 config.yaml 一个都没改。结构性盲点:审计对 cron 副本应用了"人工多处同步 = 漂移风险"原则,却没套用到"手动改 4 份 config.yaml"。建议:做成五行的幂等脚本(读 4 路径 → 无 timeout 才插入 → 打印 diff → 无 --yes 不落盘)。

**2.2 `~/.agents/skills/geo-job-hunt/` 依然没有 git**——I6 第二次被记录为"建议,未执行"。全篇唯一"不做才是风险"的项。`git init` + `.gitignore` 排除 `logs/*.json`,30 秒,无下行风险。破例建议不等 v6,现在就做。

**2.3 `apply_batch.py` 里有一个"假开关"**——`--require-kind` 用 `action="store_true"` 配 `default=True`:不传是 True,传了还是 True,真正生效的是反面 `--allow-empty-kind`。修法:删掉这个 flag 或改 help 文案。一行改动。

### 3. 为什么不构成"做 v6"的理由

| 事项 | 性质 | 成本 | 是否需要"审计" |
|---|---|---|---|
| config timeout 补丁 | 已知方案,只是没执行 | 分钟级 | 不需要,直接改 |
| git init | 已知方案,只是没执行 | 秒级 | 不需要,直接做 |
| --require-kind 死开关 | 新发现,方案显而易见 | 一行 | 不需要,顺手改 |
| apply_job/call() 重复实现(S5) | 需要真实数据才能判断 | 未知 | 需要的不是审计,是一次真实投递 |

前三条是"欠的债,还就是了";第四条是"缺的数据,审计生不出数据"。v6 式审计 = 把已诊断清楚的问题重新诊断一遍(Sheeran-mean:格式工整、边际信息趋零)。

### 4. 真正值得做的下一步(不是优化,是解锁)

找一个不那么在意结果、但真实存在的岗位,手动跑一次:
```
python3 scripts/apply_batch.py --hunt <一个真实 hunt.json> --max 1
```
拿到的原始响应体,无论成功失败,都会把 OK_UNVERIFIED 变成一个真实契约——S5 能不能合并、apply 判定要不要收紧、jobKind 枚举能不能反推,全部依赖这一次真实调用。这是系统目前唯一真正的瓶颈。

### 5. 关于"面向更广受众"

pack 的受众是 Liz 自己和 Hermes/Cursor agent 生态,不是公开产品,不需要往"破圈传播"方向改。按"三个月后的自己或接手者能否低成本读懂"把关即可。SKILL/README 信息密度无虚胖,不需要重排。

**收尾**:代码和文档已经够好,够诚实,够克制。剩下的不是打磨,是执行——三个几分钟的动作,加一次真实的简历投递。
